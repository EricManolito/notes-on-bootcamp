01

REST APIs and HTTP

HTTP — the language of the web

Every time a browser loads a page, every time the Wanderlist frontend asked the backend for data, the communication happened over HTTP — HyperText Transfer Protocol. It's the agreed-upon language that clients (browsers, React frontends) and servers use to talk to each other.

HTTPS is the same thing with encryption added — the S stands for Secure. Every production web app uses HTTPS. The http.cat site maps every HTTP status code to a cat photo — a fun but genuinely useful reference when debugging why a request is failing.

Anatomy of a URL

https://eric.ddfullstack.cloud:8080/apis/wanderlist?profileId=123

https://               → protocol (secure HTTP)
eric.ddfullstack.cloud → domain (the server address)
:8080                  → port (which door on the server to knock on)
/apis/wanderlist       → path (which resource you want)
?profileId=123         → query parameter (filtering or extra info)

HTTP methods — the four actions of CRUD

HTTP MethodDatabase OpPlain English
GETSELECTRead / retrieve data
POSTINSERTCreate something new
PUTUPDATEEdit something existing
DELETEDELETERemove something

HTTP status codes

CodeMeaningWhen it appears
200OKRequest succeeded, here's your data
201CreatedPOST succeeded, new record created
400Bad RequestSomething wrong with what you sent (Zod validation failure)
401UnauthorizedYou're not logged in (isLoggedInController fired)
403ForbiddenYou're logged in but not allowed to do this
404Not FoundThat resource doesn't exist
500Internal Server ErrorSomething broke on the server side

REST — the design pattern behind our API

REST stands for Representational State Transfer. It's not a technology — it's a set of conventions for how URLs and HTTP methods should be structured so APIs are predictable and consistent.

REST conventions followed in Wanderlist

  • URLs identify resources (things), not actions: /apis/wanderlist not /apis/getWanderlist
  • HTTP methods define the action: GET to read it, POST to create it, PUT to update it, DELETE to remove it
  • A specific item is identified by its ID in the URL path: /apis/wanderlist/:wanderlistId
  • Responses always return JSON with a consistent shape: { status, message, data }

Wanderlist REST API examples

// GET — retrieve data
GET /apis/wanderlist                    // get all wanderlist items
GET /apis/wanderlist/:wanderlistId      // get one by ID
GET /apis/profile/:profileId            // get a profile by ID

// POST — create new data
POST /apis/wanderlist                   // create a new wanderlist item
POST /apis/sign-up                      // create a new profile

// PUT — update existing data
PUT /apis/wanderlist/:wanderlistId      // update a wanderlist item

// DELETE — remove data
DELETE /apis/wanderlist/:wanderlistId   // delete a wanderlist item
DELETE /apis/follow/:followId           // unfollow a profile

// Standard response shape used throughout Wanderlist:
response.json({ status: 200, message: 'wanderlist retrieved', data: result })

Query parameters vs URL parameters

// URL parameter — identifies a specific resource
// Route defined as: router.route('/:wanderlistId')
// Request URL: /apis/wanderlist/abc-123
// Access in controller: request.params.wanderlistId

// Query parameter — filters or modifies a request
// Request URL: /apis/wanderlist?visibility=public
// Access in controller: request.query.visibility

// GET requests use URL params and query params — no body
// POST and PUT requests put their data in the JSON body
// This is why passwords always go in POST requests — they don't show up in the URL

Node.js, Express, and the Request/Response Cycle

What Node.js actually is

Before the bootcamp, JavaScript only ran in the browser. Node.js changed that — it's a runtime environment that lets JavaScript run on a server, outside the browser entirely. That's the reason we could write our entire backend in TypeScript/JavaScript instead of switching to a different language like Python or Java.

When you ran npm install or npm run dev in the terminal, that was Node running. Every time you saw a package.json file, that was Node's way of tracking what your project depends on.

What Express is

Express is a framework that runs on top of Node. If Node is the engine, Express is the car — it gives you the structure to build a web server without writing everything from scratch. What Express does for us: listens for incoming HTTP requests, routes those requests to the right function, and sends a response back.

In the Wanderlist backend, every API endpoint we built in Insomnia was Express receiving a request and sending back JSON.

The Request/Response Cycle

This is the heartbeat of everything on the backend. Every single interaction between the frontend and backend follows this pattern:

Frontend (React)
    → HTTP Request
        → Express Router
            → Controller
                → Model
                    → PostgreSQL
                ← Model returns data
            ← Controller sends response
    ← Frontend receives JSON

This is the SQL → route → controller pattern introduced in the October 27th code-along. We also built it in reverse — controller → route → SQL — depending on the day.

async/await — how we handle waiting

The database doesn't respond instantly. When your code asks PostgreSQL for data, it has to wait. That's what async/await handles — it tells JavaScript "pause here until this finishes, then continue."

// Without async/await this would be a problem —
// JavaScript would move on before the data came back

export async function getWanderlistByProfileId(profileId: string) {
  const result = await sql`
    SELECT * FROM wanderlist
    WHERE profile_id = ${profileId}
  `
  return result
}

// The async keyword tells JavaScript this function will have waiting in it.
// The await keyword says "stop here until this comes back."
// Every controller function was async. Every database call used await.

The three layers — Model, Controller, Route

In the Capstone backend the code was split into three clear layers. This separation is a standard pattern called MVC (Model-View-Controller) — though in our case the "View" was handled by the React frontend.

Model

Talks directly to the database. Contains the SQL queries. Doesn't know anything about HTTP requests or responses. Example: getWanderlistByProfileId() in wanderlist.model.ts.

Controller

The middleman. Receives the request, calls the model, sends the response. Also where Zod validation lives — checking that incoming data is the right shape before it touches the database. Example: getWanderlistByProfileIdController() in wanderlist.controller.ts.

Route

The address. Tells Express which controller to call when a specific URL and HTTP method are hit. Example: router.route('/:profileId').get(getWanderlistByProfileIdController) in wanderlist.route.ts.

// The flow:
// wanderlist.route.ts  →  wanderlist.controller.ts  →  wanderlist.model.ts
// (URL + HTTP method)      (validate, respond)           (SQL query)

// Example route file
router
  .route('/')
  .get(getAllWanderlistController)
  .post(isLoggedInController, postWanderlistController)

router
  .route('/:wanderlistId')
  .get(getWanderlistByIdController)
  .put(isLoggedInController, putWanderlistController)
  .delete(isLoggedInController, deleteWanderlistController)

Insomnia — testing the backend without a frontend

  • GET request → no body, data goes in the URL
  • POST request → has a JSON body, data doesn't appear in the URL
  • PUT request → update existing data, usually needs both a URL param and a JSON body
  • DELETE request → usually just a URL param identifying what to remove

The authorization token in Insomnia headers was how we verified a user was logged in — the isLoggedInController middleware checked for that token before letting the request through.

Authentication: Sign Up, Sign In, and Staying Logged In

What authentication actually solves

Authentication answers one question: who are you, and can I trust that? Every app that has user accounts needs to solve this problem. The challenge is that HTTP is stateless — every request arrives with no memory of previous requests. Authentication is the system we build to solve that.

Passwords — why we never store them directly

Storing a user's actual password in the database is one of the most serious security mistakes a developer can make. Instead we store a hash — a one-way transformation of the password. You can turn a password into a hash, but you cannot turn a hash back into the original password. When a user signs in, you hash what they typed and compare it to the stored hash.

In the bootcamp we used argon2 for hashing. The modular arithmetic analogy from Marty: dividing numbers and keeping only the remainder illustrates the one-way nature — you can always compute the remainder, but you can't reverse-engineer the original number from just the remainder.

import argon2 from 'argon2'

// On sign up — hash before storing
const passwordHash = await argon2.hash(password)
// Store passwordHash in the database, NEVER the raw password
// The hash is always exactly 97 characters — stored as CHAR(97) in PostgreSQL

// On sign in — verify against the stored hash
const isValid = await argon2.verify(storedHash, passwordAttempt)
// Returns true if they match, false if not

Activation tokens — verifying an email address

When a user signs up, we don't immediately activate their account. We send them an email with a unique activation token — a random 32-character string stored in the database. When they click the link in that email, the token is verified and the account is activated. This is the activation_token varchar(32) column in the profile table. The third-party service used to send the email in Wanderlist was Mailgun.

import { randomBytes } from 'crypto'
// Generate a random 32-character activation token on sign up
const activationToken = randomBytes(16).toString('hex')

// Store it in the profile row alongside the hashed password
// Email the user a link containing this token
// When they click it: look up the token, activate the account, clear the token

Sessions and staying logged in

Once a user is verified and logged in, the backend creates a session — a record that this user is authenticated. A session ID gets sent back to the frontend as a cookie, which the browser stores and sends automatically on every subsequent request.

This is what the connect.sid value was in Insomnia — the session cookie. When you saw authorization values in the Insomnia headers during the backend code-alongs, that was the session being passed back to prove the user was still logged in.

// On successful sign in, Express creates a session
request.session.profile = { profileId: profile.id, profileName: profile.name }

// isLoggedInController — middleware on every protected route
export function isLoggedInController(request, response, next) {
  if (!request.session.profile) {
    return response.json({ status: 401, message: 'You must be logged in', data: null })
  }
  next()  // session exists — continue to the actual controller
}

The full sign-up flow end to end

  1. User fills out sign-up form on frontend (React Router 7 Form)
  2. Action function sends POST request to backend with form data in JSON body
  3. Express routes request to signUpController
  4. Zod validates the incoming data against ProfileSchema
  5. If invalid → return 400 error, don't touch the database
  6. If valid → hash the password with argon2
  7. Generate a 32-character activation token
  8. INSERT new profile row into PostgreSQL (hashed password, token, email)
  9. Send activation email via Mailgun with token in the link
  10. Return success response to frontend
  11. User clicks email link → activation token verified → account active
  12. User can now sign in

This is why sign-up was one of the most complex code-alongs in the bootcamp — it touches Zod, argon2, PostgreSQL, an external email service, and React Router all in one feature.

Git Branching Workflow

Why branching exists

Without branching, everyone on the team is working on the same code at the same time. One person pushes a half-finished feature and suddenly nobody's code runs. Branching gives each person their own isolated copy of the codebase to work in. The work stays separate until it's ready to be combined.

The rule from the bootcamp: only merge when the code works.

The branch structure used on Wanderlist

main
  └── develop
        ├── community-integration (Eric)
        ├── post-integration
        ├── sign-up-form
        └── wanderlist-integration (Srilatha)
  • main — the production branch. Only merge into main when the whole team agrees the code is stable.
  • develop — the shared working branch. Feature branches get merged into develop first.
  • feature branches — where the actual daily work happens. Each person or feature gets its own branch off of develop.

The daily git workflow

git checkout main
git pull
git checkout develop
git pull
git checkout -b your-feature-branch   # -b flag creates a new branch

# do your work...

git add .
git commit -m 'describe what you did'
git push origin your-feature-branch

# then on GitHub: create a pull request to merge into develop

Quick reference — commands used most

git checkout main              # switch to main branch
git pull                       # pull latest from remote
git checkout -b feature-name   # create and switch to new branch
git add .                      # stage all changes
git commit -m 'message'        # commit with a message
git push origin feature-name   # push branch to GitHub
git merge develop              # bring develop into your current branch
git checkout develop           # switch to develop
docker compose down -v         # wipe containers and volumes
docker compose up              # rebuild and restart

Where things went wrong — merge conflicts

A merge conflict happens when two people edited the same file, in the same area, and git can't figure out which version to keep. It's not a bug — it's git asking "I see two different versions of this line, which one is correct?"

On Wanderlist this came up when feature branches diverged from develop for too long. The longer a branch lives without pulling in updates from develop, the more it drifts — and the more painful the merge becomes.

# Pull from develop into your feature branch regularly
git checkout develop
git pull
git checkout your-feature-branch
git merge develop

# When a conflict occurs, git marks it in the file:
<<<<<<< HEAD
your version of the code
=======
your teammate's version of the code
>>>>>>> develop

# Manually pick which version to keep, delete the markers, then:
git add .
git commit

Habits that reduce merge conflicts

  • Communicate before merging to develop — a quick Slack message "merging dashboard now" gives teammates a heads up
  • Small, frequent merges — merging one finished feature at a time is easier to untangle than one giant merge at the end of a sprint
  • Pull develop into your branch before you start each day — you find out early if something conflicts rather than discovering it right before a deadline
  • Never force push to develop or main — force pushing rewrites history and can overwrite a teammate's work silently

JavaScript Methods and Function Syntax

Functions — the building blocks of everything

A function is a reusable block of code that does a specific job. You define it once and call it whenever you need it. In the bootcamp we used a few different ways to write them, and they all do the same thing — just with different syntax.

// Function declaration
function greet(name) {
  return 'Hello, ' + name
}

// Function expression — storing a function in a variable
const greet = function(name) {
  return 'Hello, ' + name
}

// Arrow function — the shorthand version we used most in React
const greet = (name) => {
  return 'Hello, ' + name
}

// Arrow function — even shorter when it's just one line
const greet = (name) => 'Hello, ' + name

The parts of a function: the name tells you what it does, the parameters are the inputs it expects (called arguments when you actually pass values in), the body is the code inside the curly brackets, and the return value is what it hands back when it's done.

Higher-Order Functions — map, filter, reduce

These are array methods that take a function as an argument and run it on each item in the array. George and Marty used the food analogy to introduce these — map cooks the food, filter picks what you want, reduce consumes it all into one thing.

.map() — transform every item, get a new array back

Use this when you want to do something to every item and keep all of them.

const numbers = [1, 2, 3, 4]
const doubled = numbers.map((num) => num * 2)
// doubled = [2, 4, 6, 8]

// In React this is how we render lists:
const pizzas = ['Cheese', 'Pepperoni', 'Supreme']
return (
  <ul>
    {pizzas.map((pizza) => (
      <li key={pizza}>{pizza}</li>
    ))}
  </ul>
)

.filter() — keep only the items that pass a test

const numbers = [1, 2, 3, 4, 5, 6]
const evens = numbers.filter((num) => num % 2 === 0)
// evens = [2, 4, 6]

.reduce() — collapse the whole array into one value

const numbers = [1, 2, 3, 4]
const total = numbers.reduce((acc, num) => acc + num, 0)
// total = 10
// The 0 at the end is the starting value of the accumulator

Chaining — combining methods together

const numbers = [1, 2, 3, 4, 5, 6]

const result = numbers
  .filter((num) => num % 2 === 0)   // keep evens: [2, 4, 6]
  .map((num) => num * 10)            // multiply: [20, 40, 60]
  .reduce((acc, num) => acc + num, 0) // sum: 120

Action and Loader functions in React Router 7

These are specific to React Router 7 (what we used in Wanderlist). They replaced the old way of fetching and submitting data.

loader — runs before the page loads

Its job is to fetch data and hand it to the component. Think of it as the setup crew — it gets everything ready before the curtain goes up.

export async function loader({ request }) {
  const response = await fetch(`${process.env.REST_API_URL}/wanderlist`, {
    headers: { Cookie: request.headers.get('Cookie') ?? '' }
  })
  const body = await response.json()
  return body.data
}

export default function WanderlistPage() {
  const wanderlist = useLoaderData()
  return (
    <ul>
      {wanderlist.map((item) => (
        <li key={item.wanderlistId}>{item.wanderlistTitle}</li>
      ))}
    </ul>
  )
}

action — runs when a form is submitted

export async function action({ request }) {
  const formData = await request.formData()
  const title = formData.get('wanderlistTitle')
  await fetch(`${process.env.REST_API_URL}/wanderlist`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json',
                Cookie: request.headers.get('Cookie') ?? '' },
    body: JSON.stringify({ wanderlistTitle: title })
  })
  return redirect('/wanderlist')
}

export default function NewWanderlistPage() {
  return (
    <Form method='post'>
      <input name='wanderlistTitle' type='text' />
      <button type='submit'>Add to Wanderlist</button>
    </Form>
  )
}

The rule of thumb from the bootcamp: loader for reading data, action for writing data.

TypeScript and Zod

What TypeScript is and why we used it

JavaScript is flexible — maybe too flexible. You can pass a number where a function expects a string and JavaScript won't stop you. TypeScript adds a layer on top of JavaScript that catches those mistakes before the code ever runs.

TypeScript is a superset of JavaScript — meaning all valid JavaScript is also valid TypeScript. You're not learning a new language, you're adding a safety layer. At the end of the day the TypeScript compiler converts everything back to plain JavaScript. The browser never sees TypeScript directly.

In the bootcamp we wrote .ts files for backend logic and .tsx files for React components. The x in .tsx just means "this TypeScript file also contains JSX."

Types — telling your code what to expect

// Basic types
let profileName: string = 'Eric'
let age: number = 44
let isLoggedIn: boolean = false

// TypeScript infers the type if you assign immediately
let city = 'Albuquerque'  // TypeScript already knows this is a string

// Function parameters — TypeScript will catch wrong types at write time
function getProfileById(id: string) {
  // if you pass a number, TypeScript flags it before runtime
}

Custom types and the type keyword

export type Pizza = {
  image: string
  name: string
}

// Now everywhere Pizza is used, TypeScript knows exactly what it should look like
const pizzas: Pizza[] = [
  { image: 'cheese.jpg', name: 'Cheese' },
  { image: 'pepperoni.jpg', name: 'Pepperoni' }
]
// Pizza[] syntax means "an array of Pizza objects"

Type Props — passing typed data into React components

type ProfileCardProps = {
  profileName: string
  bio: string
  imageUrl: string
}

export function ProfileCard({ profileName, bio, imageUrl }: ProfileCardProps) {
  return (
    <div>
      <img src={imageUrl} alt={profileName} />
      <h2>{profileName}</h2>
      <p>{bio}</p>
    </div>
  )
}

What Zod is

TypeScript is a compile-time safety tool — it catches type errors while you're writing code. But once data arrives from the outside world — a form submission, an API request, user input — TypeScript can't verify it. That data is unknown until it arrives at runtime.

Zod is a runtime validation library. Where TypeScript says "this should be a string," Zod says "let me actually check that this is a string right now, while the app is running, and tell you clearly if it isn't."

In the Wanderlist backend, every piece of incoming data passed through a Zod schema before it touched the database. This is the security layer Marty introduced as the Fundamental Theorem of User Input — never trust data coming in from outside your app.

Zod schemas — defining the shape of incoming data

import { z } from 'zod'

export const ProfileSchema = z.object({
  profileName: z.string().min(1).max(48),
  profileEmail: z.string().email(),
  password: z.string().min(8),
  profileAboutMe: z.string().max(256).nullable()
})

// z.infer generates a TypeScript type from the schema — no duplication needed
export type Profile = z.infer<typeof ProfileSchema>

safeParse — checking data in the controller

export async function postSignUpController(request: Request, response: Response) {
  // Check the incoming data against the schema
  const validation = ProfileSchema.safeParse(request.body)

  // If it doesn't match, send back a clear error — don't touch the database
  if (!validation.success) {
    return response.json({ status: 400, message: validation.error.errors, data: null })
  }

  // Data passed validation — safe to use
  const { profileName, profileEmail, password } = validation.data
  // ... continue to hash password, insert into database, etc.
}

.pick() and .omit() — reusing schemas

// Full schema defined once
export const ProfileSchema = z.object({
  profileName: z.string(),
  profileEmail: z.string().email(),
  password: z.string(),
  profileAboutMe: z.string().nullable()
})

// Sign-in only needs these two — pick pulls them out
export const SignInSchema = ProfileSchema.pick({
  profileEmail: true,
  password: true
})

// Sign-up needs everything except aboutMe — omit removes it
export const SignUpSchema = ProfileSchema.omit({
  profileAboutMe: true
})

How TypeScript and Zod work together

They complement each other rather than overlap:

ToolWhen it runsWhat it catches
TypeScriptCompile time (while writing code)Wrong types passed between functions, missing properties, typos in property names
ZodRuntime (while app is running)Bad data from forms, API requests, user input — anything from outside your app

TypeScript makes sure your teammates pass the right types when calling your functions. Zod makes sure the outside world — forms, API requests, user input — sends data your app can actually use. Together they form the two-layer validation approach that ran through the entire Wanderlist backend.
